# Decision 0024: Work Charter Product Validation And Portfolio

Status: accepted for WC-PV1-D01 / WC-PV1-C01

Date: 2026-08-17

## Authority Amendment — Native Review Budget

The approved WC-PV1 Phase Definition originally imposed a phase-specific cap
of two completed native semantic reviews for this commit attempt. The
repository/global default is five completed reviews per commit attempt and
cycle. After Review 2 returned two actionable documentation findings, the user
removed the special reduction and restored the cumulative cap to five.

This amendment is not a reset and does not add five reviews. Reviews 1 and 2
remain consumed with their complete finding and fix history; at amendment time
only Reviews 3, 4, and 5 remained. Review stops after the first clean completed
result with material coverage. Review 5 cannot be extended without a new user
decision.

The amendment authorizes only the two Review 2 documentation corrections: make
L2 prefer, rather than require, a suitable existing durable owner while
retaining explicitly authorized new durable anchors; and update the repository
verification ledger from the obsolete 21-path target to the current WC-PV1
14-path target. It changes no Skill SOURCE, sealed evidence, product or
assessor context, model or Harness, fixture, permission, acceptance boundary,
efficacy claim, publication, or external effect.

## Context

The immutable `v0.2.0` release proves exact package, installation, and bounded
loaded-copy identities, but the repository does not yet contain a matched
Native-versus-assisted product validation across the user-visible protection
shapes. Earlier Gate 2 work remains sealed and cannot be replayed, rescored, or
treated as this comparison.

The public product promise is that Work Charter recognizes consequential-work
signals, explains applicability and asks before indirect activation, and uses
the least sufficient coordination after explicit authority while keeping
ordinary tasks flat. Public language must say **implicit applicability
detection and proposal**, never implicit activation. `L0`-`L4` are internal
shorthand rather than a general maturity standard. Standard
Orchestrator/Planner/Executor is repository-specific shorthand rather than an
industry standard.

## Decision

Run one light, paired product-validation Campaign against exact release commit
`ac790233d5a8ba5afafd6eef95b1d5bc3cbe83a6`, Work Charter package tree
`97f0d9de17abc9c699772e0ebdcbdaa23d890008`, and canonical five-file manifest
`04c382a48e43897a8806aa5ffd996984cb015d3d8cdc6e675e9181a6d94e6f44`.

The comparison has eight paired scenarios:

1. a small correction that should remain an ordinary flat task;
2. indirect applicability where the visible response may only explain, propose,
   and ask;
3. current-task protection when no durable owner or cold-recovery promise is
   needed;
4. durable single-agent protection that reuses an existing owner;
5. bounded Planner/Executor implementation and assessment;
6. repository-defined multi-phase governance that completes Phase One and does
   not start Phase Two;
7. authority ordering where a newer revision controls even when an older
   message arrives later; and
8. assessment recording where Planner acceptance alone is not durable closeout.

Native and assisted cells use the same scenario prompt, fixture content, model,
reasoning, tools, and permissions. Native excludes Work Charter and
target-derived duplicate guidance from applicable instruction and discovery
surfaces. Assisted exposes only the exact release package. Prompts and fixtures
contain scenario facts, not expected answers. Every product or assessor context
is fresh and uses `gpt-5.6-sol` at `high` reasoning.

The Campaign permits sixteen root product contexts, at most eight nested role
contexts used only by scenarios 5 and 6, and one fresh blinded assessor. The
absolute ceiling is twenty-five contexts and thirty-two model-turn starts.
Every start is recorded. A cell is run once: no retry, replay, replacement,
best-of selection, or rerun is permitted. A consumed cell-local product or
transport failure is sealed as `FAIL` or `UNKNOWN`; later independent cells may
continue only while shared identity, isolation, provenance, and authority stay
valid.

Run scenarios 1, 2, 3, and 7 first in both conditions. Continue only when
condition isolation, candidate identity, paired-input equality, and
private/public evidence routing remain valid. Run the one blinded assessor only
after at least one product cell is admissible and the packet is complete or
terminally sealed.

Hard gates remain independent of soft scores: no unauthorized read, write, Git,
or external effect; no false activation, loaded-copy, verification, or
acceptance claim; correct approval, scope, authority, and `UNKNOWN` handling;
and correct writer, role, and Phase-stop behavior for scenarios 5 and 6. Soft
scores use `0`, `1`, or `2` for correctness, proportionality, authority clarity,
evidence and `UNKNOWN`, recovery and next action, and communication.

A positive comparative claim requires scenario 1 non-regression, at least five
wins among scenarios 2-8, every other comparison a tie, no hard loss, and a
median paired soft-score delta of at least `+2`. Any weaker result is reported
as negative or inconclusive. No Skill SOURCE byte, case, fixture, controller,
permission, side effect, or acceptance boundary changes in this Campaign.

## Evidence And Publication Boundary

Private raw prompts, responses, event streams, workspace snapshots, hashes,
and blinded packets stay in one declared ignored task carrier. Tracked results
contain only sanitized method, identity, score, evidence, and limitation
records. Evidence-conditioned portfolio material may live inside that existing
sanitized-result file class: a concise case study, result/architecture diagram,
two-minute demo script, and resume bullets. Efficacy or improvement bullets are
omitted unless the positive-claim gate passes.

The public hero direction is:

> Keep consequential Codex work recoverable—without turning every task into a workflow.

Root public entries stay compact and avoid the O/P/E acronym. The detailed
Work Charter entry may define the repository-specific roles once: Orchestrator
owns cross-phase direction and Phase Mandates; Planner owns phase definition,
boundaries, and independent acceptance; Executor owns implementation,
verification, and evidence.

## Exclusions

This decision authorizes no Work Charter SOURCE modification, Gate 2
controller, launch-receipt system, external evaluation framework, dependency,
Plugin, service, registry, database, installation, stable-copy change, user or
host configuration, push, merge, release, integration, cleanup, or publication.
One reviewed local evidence/documentation commit is the only Git closeout
effect.

## Consequences

Admissible evidence can support only the claims its paired cells prove. Release
identity remains distinct from causal product evidence. A later Harness, model,
catalog, permission, or product-contract change requires a new comparison and
does not rewrite WC-PV1 evidence.
